# Playwright(Python)によるE2Eテスト自動化の練習

練習用ECサイト「Sauce Demo」を題材に、Playwright + pytest でテスト自動化に取り組んだリポジトリです。

## 使用技術
- Python / pytest / Playwright
- GitHub Actions(GitHubにpushするたびに自動実行)

## 構成
- `tests/`：直下の test_login.py / test_cart.py / test_logout.py
- `pages/`: 画面ごとの部品と操作をまとめたPage Object
- `conftest.py`: 「ログイン済み」の事前条件を作るfixture

## 動かし方
'pip install -r requirements.txt'
'playwright install'
'pytest --headed'

## 自動化の方針
### 自動化したもの
- ログイン・カート内の商品の増減：ECサイトの基本導線
  - ログイン(成功/パスワード誤り): 毎回確認が必要で、手順が固定のため
  - カートへの追加: 購入フローの入口のため
  - カートからの削除: 購入フロー内での変更部分のため
  - ログアウト: ログイン状態が正しく終わることは、基本導線の一部のため

### あえて自動化していないもの
- 画面の見た目・デザインの確認: 人の目で判断する部分で、自動化の費用対効果が低いため
- 未対応(今後の課題)
  - 購入完了までの全手順
  - 商品の並び替え
  - など

### 工夫した点
- **事前条件の共通化(fixture)**: 「ログイン済みの状態」を `conftest.py` の1か所にまとめ、各テストから呼ぶだけにした。ログイン手順の重複をなくし、ログイン画面が変わっても修正箇所が増えないようにした
- **画面単位での整理(Page Object)**: 部品の指定と操作を `pages/` にまとめ、テスト側は「バックパックをカートに入れる」のように読める形にした。ログアウトは、実際にはメニューが商品一覧画面にあるため、画面の実態に合わせて `InventoryPage` に置いた
- **成功・失敗の両パターン**: ログインは、成功とパスワード誤りの両方を確認している
- **事前条件の確認**: カートからの削除テストでは、削除の前に「カートが1件になっている」ことを確認し、前提が崩れた場合に原因を切り分けやすくした
- **画面の変更に強い指定**: 部品の指定には、画面の見た目に左右されにくい `data-test` 属性を優先して使った
- **エビデンスの自動保存**: GitHub Actionsで、スクリーンショットを毎回、動画とトレースを失敗時に保存し、テストが失敗した場合でも、Actionsの画面からダウンロードできるようにした
